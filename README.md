# SDN Controller Benchmarking Testbed

An open-source testbed for benchmarking OpenFlow SDN controllers under a
reproducible, seeded TCP workload. It accompanies the paper *(ICC 2027)*; the
testbed itself is the contribution.

**Pipeline.** Mininet + Open vSwitch emulate the network; iperf3 generates TCP
flows between random host pairs at a fixed flow rate; an instrumented
controller app logs per-Packet-In handler timing and per-second
Packet-In/FlowMod counts; a psutil monitor logs controller CPU and memory; a
shell orchestrator runs each experiment and an aggregator appends one row per
run to `summary_v2.csv`.

Two controllers are included, running the same L2 learning-switch logic:
**Ryu 4.34** and **OS-Ken**.

---

## Repository layout

```
controller/   ryu_instrumented_switch.py, osken_instrumented_switch.py  (instrumented L2 apps)
topology/     star_topo.py, fat_tree_topo.py (two-tier tree), mesh_topo.py (experimental)
scripts/      run_experiment.sh / run_experiment_osken.sh   one run (Ryu / OS-Ken)
              run_matrix_*.sh                               full sweeps
              run_mininet_iperf.py                          topology + iperf3 traffic
              iperf_pool.py                                 iperf3 server-pool sizing, port assignment
              log_system_metrics.py                         psutil CPU/RSS monitor
              phase_times.py                                per-phase timing of a run
analysis/     aggregate_results.py   per-run aggregation -> summary_v2.csv
              recompute_cpu.py       CPU without the first monitor sample -> cpu_recomputed.csv
              plots_v4.py            paper figures and tables
results/                Ryu:    summary/summary_v2.csv, summary/cpu_recomputed.csv, figures_v4/
results_osken/          OS-Ken: summary/summary_v2.csv, summary/cpu_recomputed.csv
docs/         ADAPTER.md (controller contract), ENVIRONMENT.md (exact versions)
```

Raw per-run outputs (`results*/raw/`) are not in the repository; they are
regenerated by running experiments.

## Requirements

- Linux with root access (Mininet needs `sudo`). Tested on Ubuntu 24.04.2,
  kernel 7.0 — exact versions in [`docs/ENVIRONMENT.md`](docs/ENVIRONMENT.md).
- Tested on Ubuntu 24.04.2; the install steps below have not been verified on
  a fresh machine.
- System packages (apt): Mininet 2.3.0, Open vSwitch 3.3.4, iperf3 3.16
  (needs `--fq-rate`, Linux only), and for OS-Ken runs `python3-os-ken` 2.8.1.
- Python **3.10** for the Ryu virtualenv (the version used for the paper;
  Ryu 4.34 is unmaintained and was not tested on newer Python). On Ubuntu
  24.04, install it e.g. from the deadsnakes PPA.

Mininet and OVS run with the system `/usr/bin/python3` under sudo; Ryu, the
monitor, the aggregator and the plotting script run in the virtualenv.

## Install

```bash
# 1. System packages
sudo apt install mininet openvswitch-switch iperf3 python3-os-ken

# 2. Virtualenv (the run scripts expect it at ./venv_py310, fallback ./venv)
python3.10 -m venv venv_py310
source venv_py310/bin/activate
pip install --upgrade pip
pip install -r requirements.txt          # pinned versions used for the paper

# 3. Ryu 4.34 from source, with the patches needed on current setuptools/eventlet
wget https://github.com/osrg/ryu/archive/refs/tags/v4.34.tar.gz
tar -xzf v4.34.tar.gz
cd ryu-4.34
sed -i '27d' setup.py                    # remove the setuptools hook ...
sed -i '/import ryu.hooks/d' setup.py    # ... and its import
sed -i '109,112d' ryu/app/wsgi.py        # drop the ALREADY_HANDLED dependency
sed -i '109i\class _AlreadyHandledResponse(Response):\n    pass' ryu/app/wsgi.py
pip install --no-deps -e .               # dependencies are pinned in requirements.txt
cd ..
ryu-manager --version                    # should print 4.34
```

The run scripts call `sudo` several times per run (Mininet, `mn -c`, `pkill`,
`chown`). For unattended sweeps, configure passwordless sudo for those
commands or keep the sudo timestamp fresh.

## One run

```bash
# scripts/run_experiment.sh N RUN_ID FPS TOTAL_TIME FLOW_DURATION SEED TOPO
scripts/run_experiment.sh 4 SMOKE_STAR_N4_F200 200 20 2 1241 star          # Ryu
scripts/run_experiment_osken.sh 4 SMOKE_STAR_N4_F200 200 20 2 1241 star    # OS-Ken
```

- `TOPO`: `star`, `tree` (alias `fattree`; recorded as `fattree` in the data),
  or `mesh` (experimental, see Known limitations).
- Environment variables (defaults = paper settings): `FQ_RATE=2M` (per-flow
  iperf3 `--fq-rate` pacing; `0` = unpaced), `HOST_BW=0` (Mbit/s tc limit on
  host–switch links; `0` = none), `KEEP_IPERF_JSON=0` (`1` keeps the per-flow
  iperf3 JSONs in `iperf_json/` instead of deleting them after aggregation).
- Output: `results/raw/<RUN_ID>/` (OS-Ken: `results_osken/raw/<RUN_ID>/`), and
  one row appended to `results/summary/summary_v2.csv`
  (`results_osken/summary/summary_v2.csv`). **These are the paper's data
  files**: prefix trial run IDs with `SMOKE` (`plots_v4.py` skips such rows) or
  work on a copy.
- A run takes ~30–40 s wall clock; the per-phase breakdown is printed at the end
  and saved in `phase_times.json`.

## Full matrix (as in the paper)

N = 4, 8, 16, 32, 64 hosts × FPS = 25, 50, 100, 200 flows/s × 10 repetitions,
20 s runs, 2 s flows, seed = B_T + 10N + FPS + rep (B_T = 1000 star,
2000 tree): 400 runs per controller.

```bash
tmux new -s sweep
( scripts/run_matrix_star.sh \
  && scripts/run_matrix_fattree.sh \
  && scripts/run_matrix_osken_star.sh \
  && scripts/run_matrix_osken_fattree.sh ) 2>&1 | tee "sweep_$(date +%F_%H%M).log"
```

Run the matrices **sequentially, never in parallel**: every run starts with
`sudo mn -c`, kills leftover controllers, and uses OpenFlow port 6653. The four
matrices take roughly 13–18 h in total.

### `summary_v2.csv` (one row per run)

| Column | Meaning |
|---|---|
| `run_id`, `topology`, `n_hosts`, `flows_per_sec`, `rep`, `total_time`, `flow_duration`, `seed` | run parameters (`topology` is `star` or `fattree`) |
| `flow_count` | iperf3 client JSONs that parsed (legacy; includes failed flows) |
| `total_throughput_bps` | legacy: sum of per-flow mean send rates over all flows — **not** aggregate network throughput |
| `total_retransmits` | sum of sender-side TCP retransmissions |
| `avg_packet_in_rate`, `avg_flow_mod_rate` | mean of the per-second counts in `controller_metrics.csv` |
| `proc_latency_p50_ms`, `proc_latency_p95_ms` | p50 / p95 of `proc_time_ms` (handler time, see below) |
| `avg_cpu_percent` | mean controller CPU (% of one core) over all monitor samples — **includes the first-sample artifact; use `cpu_recomputed.csv`** |
| `avg_mem_mb` | mean controller RSS (MiB) |
| `attempted_flows`, `successful_flows`, `failed_flows`, `success_rate` | iperf3 flow outcomes (a flow fails if its JSON has an `"error"`) |
| `delivered_throughput_bps` | Σ `end.sum_sent.bytes` × 8 / `total_time` over successful flows (see Known limitations) |
| `servers_per_host`, `port_collisions` | iperf3 server-pool size and port-reuse events |
| `host_bw_mbit`, `fq_rate` | link limit and per-flow pacing used |
| `actual_launch_duration_s`, `achieved_fps` | how long launching all flows took; launched flows / that duration |

### `cpu_recomputed.csv` (one row per run)

`run_id, avg_cpu_percent_raw, avg_cpu_percent_nofirst, n_samples, first_sample`
— produced by `analysis/recompute_cpu.py` from the raw `system_metrics.csv`.
`avg_cpu_percent_raw` equals `avg_cpu_percent` in `summary_v2.csv`;
`avg_cpu_percent_nofirst` drops each run's first sample and is what the paper
reports.

## Metric definitions

- **Workload facts (not bugs, but must stay documented):** flow entries have no
  idle/hard timeout and ARP is static, so Packet-Ins occur only on first
  contact per directed MAC pair per switch; controller load is bounded by unique
  pairs, not FPS.
- **Latency metric definition:** `proc_time_ms` is measured from Packet-In
  *handler entry* to after the response is sent (FlowMod+PacketOut, or flooding
  PacketOut). It excludes event-queue wait. Flood events are included.

More precisely, "sent" means the last `send_msg` has returned, i.e. the message
was serialized and queued on the datapath's send queue; the socket write is not
included. Values are milliseconds, from `time.perf_counter()`.

- **Controller CPU:** psutil `cpu_percent` of the controller PID, sampled every
  1 s by a separate process; % of one core.

## Regenerating the paper figures and tables

```bash
source venv_py310/bin/activate
# (only if you have the raw runs locally; the repository already contains the output)
python3 analysis/recompute_cpu.py
python3 analysis/plots_v4.py \
    --summary results/summary/summary_v2.csv \
    --osken   results_osken/summary/summary_v2.csv \
    --outdir  results/figures_v4
```

Outputs: `fig_latency_vs_fps`, `fig_scalability_vs_hosts` (PDF + PNG),
`table_hosts.tex`, `table_osken.tex`, `paper_numbers.txt`. CPU statistics use
`avg_cpu_percent_nofirst` from `cpu_recomputed.csv` next to each summary
(`plots_v4.py` warns and falls back to `avg_cpu_percent` if it is missing).

### About the CPU numbers

The published `summary_v2.csv` was produced with the **pre-fix** monitor, which
took its first sample immediately after priming psutil. That first window
lasted microseconds, and because process CPU time advances in 10 ms ticks the
sample was either 0 or a spurious value of thousands of percent (9 of 800
runs). The paper's CPU figures drop each run's first sample
(`analysis/recompute_cpu.py`), which is equivalent to the fixed monitor now in
`scripts/log_system_metrics.py` (it sleeps one interval before every sample).

## Adding a topology

1. Create `topology/<name>_topo.py` with a Mininet `Topo` subclass whose
   `build(self, n)` creates hosts named **`h1` … `hN`** (the traffic generator
   relies on these names) and switches named `s<number>`.
2. Register it in `get_topo()` in `scripts/run_mininet_iperf.py` (add an alias
   to `TOPO_ALIASES` if needed).
3. Copy a matrix script, pass the new name as the last argument of
   `run_experiment.sh`, and give it its own seed base `B_T`
   (1000 star, 2000 tree and 3000 mesh are taken).

Topologies with loops need a controller with loop prevention (see mesh below).

## Adding a controller

The contract — forwarding logic, timing points, CSV schemas, `OUTDIR`, the
cooperative per-second logger, and the run-script lifecycle (start, PID,
readiness, stop) — is in [`docs/ADAPTER.md`](docs/ADAPTER.md), with the
complete Ryu → OS-Ken port as a worked example. Today a controller is added by
porting the app and copying `run_experiment.sh` and a matrix script; a unified
`--controller` option is planned.

## Known limitations

- **Packet-In load is bounded by unique directed host pairs**, not by flow
  rate, because flow entries are permanent and ARP is static (see Metric
  definitions). A configurable idle timeout is planned.
- **Handler time** excludes event-queue wait and the socket write.
- **"Tree" is a two-tier tree**, not a k-ary fat-tree: 1 core switch,
  ceil(N/4) edge switches, ≤ 4 hosts each, no redundant paths.
- **Mesh is experimental**: it has loops and the reference controller has no
  STP, so flooded broadcasts cause storms. It is not part of the published
  results.
- **Ryu vs OS-Ken is confounded by the interpreter**: the OS-Ken runs used the
  system `osken-manager` (os-ken 2.8.1, Python 3.12, eventlet 0.35.2), the Ryu
  runs Python 3.10 with eventlet 0.33.3. See `docs/ENVIRONMENT.md`.
- **`delivered_throughput_bps` overstates the delivered rate.** In the
  published runs it is ≈1.31× the nominal paced load
  (FPS × 2 s × 2 Mbit/s / 20 s). It is computed from iperf3's sender-side
  `end.sum_sent.bytes`, which counts bytes *written to the socket*, including
  data still in the send buffer when the test ends — not bytes delivered.
  A verification run (star, N = 4, 200 fps, `KEEP_IPERF_JSON=1`; 4000/4000 flows
  ok) shows this directly: per flow, the sender reported 655,360 B and the
  receiver 393,216 B (`sum_sent`/`sum_received` = 1.67 on 99.8% of flows),
  against a nominal 500,000 B (2 Mbit/s × 2 s), i.e. 1.31× and 0.79× nominal.
  The sender wrote 3 blocks in the first second, more than the 2 Mbit/s pacing
  can put on the wire, which is the send buffer filling up, not a rate
  overshoot. Both counters move in whole 128 KiB iperf3 blocks, which is coarse
  for a 500 KB flow, so neither is exact at this flow size; the delivered
  volume lies between the two. `end.sum_received.bytes` (a lower bound) is the
  more accurate field and should be used in future versions.
  `total_throughput_bps` is a legacy sum of per-flow rates and is not aggregate
  throughput either.
- **CPU, first sample**: see "About the CPU numbers".
- **Single machine**: traffic generators, switches, controller and monitor share
  the same CPUs.
- **No controller readiness check**: the run script waits a fixed 1 s after
  starting the controller (switches retry the connection).
- **Port reuse**: the iperf3 server pool is sized for < 0.01% port collisions;
  the published sweep had 49 per controller (out of 750,000 flows), all
  recorded in `port_collisions`.
